## 3. Why windows is slow (measured before anything moved)

Windows is **1.8×** ubuntu per job (196/105, 192/110, 177/97, 159/90),
not 3×. Per target, from the logs of nightly
39234506264 (windows jobs 118000262107, 118000262151, 118000262372;
ubuntu 118000262245, 118000262370, 118000262186):

| target | windows s | ubuntu s | ratio | spawns lupin |
|---|---|---|---|---|
| run_corpus | 7,758 | 5,176 | 1.50 | no |
| doc_truth | 6,394 | 3,736 | 1.71 | yes |
| export | 4,388 | 2,962 | 1.48 | yes |
| cli | 3,948 | 2,573 | 1.53 | yes |
| region_machine | 2,437 | 1,313 | 1.86 | no |
| rule_registry | 2,137 | 1,326 | 1.61 | no |
| divergence | 1,894 | 1,254 | 1.51 | no |
| fuzz_smoke | 406 | 262 | 1.55 | no |

The in-process targets are as slow as the ones that spawn the binary, so
it is not process start-up or antivirus-shaped I/O on each exec; it is the
same debug-build interpreter running 1.5–1.9× slower on the windows
runner. Against the contract's candidates:

- **Cold cache, debug builds.** The build is not the cost: the `test`
  step compiles in 46–61 s on windows (54 / 61 / 46 s in the three shards
  above; ubuntu 32 s), clippy 0.6 min, the toolchain 0.2 min, out of a
  148–188 minute job. A cache that hits saves at most that and a windows
  restore of `target/` costs about as much. **Not taken.**
- **Release-profile test binaries.** Only a profile that keeps
  `debug-assertions` and `overflow-checks` keeps the same assertions: the
  crate branches on `cfg!(debug_assertions)` (`src/lib.rs` `BUILD_PROFILE`
  and `is_debug_build()`, which `diff-run` refuses on; the lend's
  agreement check at `src/eval/mod.rs` 8969) and `region_machine`'s
  forest test reads "after every mutation, a debug assertion re-walks the
  region graph". So the time is in work the assertions themselves do, and
  an assertion-keeping profile keeps it. Measured on kasumi at `0e536e8`
  (`--config profile.ci.inherits="release"`, `debug-assertions=true`,
  `overflow-checks=true`; each run `taskset` to 4 cpus with
  `--test-threads=4`, debug and ci side by side on the same loaded host):
  `region_machine` **2,438 s debug, 2,028 s ci: 1.20×**, for a build of
  42 s against 31. A sixth off the in-process targets, bought by testing a
  differently optimized binary than every other job tests (the stack each
  frame takes changes, and stack depth is what the windows smoke caught in
  run 38975226904): **not taken**. (`cli`, the spawning target, in §5.)
- **The ladder's serial rungs.** The windows ladder is 159 min to
  ubuntu's 90: the corpus walk 43.6 and the bundle 41.1 min on windows
  against 42.2 and 42.5 on ubuntu in 39234506264 (that night's windows
  ladder was 96.5 min, its fastest of the 17). Its steps are serial by
  construction (a walk, then a bundle exported twice and byte-compared).
- **More shards under the cap.** The shard key is one table for every OS
  (`ci/test-shards.sh`: "so a shard can never drift from another OS's").
  `run_corpus` is one binary of 7,758 s (129 min) on windows, the floor of
  any target-level split. Four shards would cut the widest windows job
  from 188 to about 133 min and the job-minutes not at all (each shard
  pays its own set-up and build), and would add a shard to ubuntu and
  macOS too: one more long job in the merge gate. The slot budget is
  job-minutes and slots held at once, not windows wall. **Not taken.**
- **The smoke's cap.** The windows smoke has had a 30-minute cap since
  r32 and runs 12–20 minutes; it stays in the merge gate, unchanged.
