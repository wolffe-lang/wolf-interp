So, predicted and to be confirmed by the red test:
- The cause is d45084b alone: it replaced std's CommandExt::exec, which
  sets SIGPIPE back to the default before it execs, with nix's execve,
  and POSIX execve keeps an IGNORED signal ignored. Rust's runtime ignores
  SIGPIPE before main, so every image 0.1.57 execs starts with it ignored.
  e603e6d touches only the spawn paths and is not involved.
- The issue's premise about the MASK does not hold at Rust 1.97.1: no
  path, 0.1.56's std exec included, empties an inherited mask. The mask is
  not part of the regression. With a plain start the image's mask is
  already empty for SIGPIPE at fb054c8b.
- Every other program-starting path (os_spawn, os_spawn_with, os_spawn_fds,
  os_spawn_job with a group, lupin's internal `sh -c kill` for a group,
  the differ's counterparty) goes through std's Command and hands the
  child SIGPIPE at its default: no leak. os_fork starts nothing (refused).

Rulings (recommend; implement the recommendation):
- R-r41e-1: (A) a safe API before the direct execve. Recommend A with
  signal-hook's safe `flag::register(SIGPIPE, …)`: it makes SIGPIPE
  CAUGHT instead of ignored, and POSIX execve sets every caught signal to
  its default in the new image; nix's own `signal`/`sigaction` are unsafe.
  Reject (B): measured above, std's exec re-runs a #! script under /bin/sh
  when its interpreter has no header, and the header guard admits #!, so
  B reopens R-is81-1's shell fallback (also a check-then-exec race).
  (C) is not needed. Pin signal-hook =0.3.18 (MIT OR Apache-2.0, default
  features off); predicted Cargo.lock change: two packages added
  (signal-hook, signal-hook-registry), none bumped, errno and libc reused.
- R-r41e-2 (new): the mask across os_exec. (A) pass the inherited mask
  through unchanged, as 0.1.56, every spawn path and a native image do;
  (B) unblock SIGPIPE at exec only. Recommend A: no mask change.
